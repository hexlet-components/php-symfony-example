## Приложение курса

Афиша содержит те же сущности, маршруты и формы, которые разбираются в уроках. В корне репозитория находится итог приложения. Каталог _.examples/base/_ хранит общую заготовку, а _.examples/steps/_ содержит изменения по урокам. Скрипт _.examples/prepare.php_ копирует заготовку и последовательно накладывает изменения до указанного слага. Он готовит результат урока в новом каталоге и отказывается перезаписывать существующие файлы.

Проверенный набор использует PHP 8.5.12, Symfony 8.1.11, Doctrine ORM 3.8.0, DBAL 4.6.0 и PHPUnit 13.4.7. PHP должен содержать расширения intl, mbstring и pdo_sqlite. Composer устанавливает зависимости из сохранённого _composer.lock_, а _symfony.lock_ фиксирует применённые recipes. Установка полного профиля зависимостей доступна с первого состояния, код возможностей появляется по мере уроков. Turbo, Stimulus и Doctrine Messenger исключены из профиля.

Из каталога php-symfony-example состояние урока восстанавливается такой командой.

```bash
php .examples/prepare.php first-test /tmp/agenda-first-test
cd /tmp/agenda-first-test
composer install
php bin/phpunit
php -S 127.0.0.1:8000 -t public
```

Страница открывается по адресу `http://127.0.0.1:8000/events`. У состояния `first-project` стартовая страница находится по адресу `/`. Состояния до `migrations` работают без созданных таблиц БД. Ранние изменения данных предназначены для локального учебного запуска. Защита записи появляется в `authentication`, проверка владельца в `authorization`.

После `migrations` схема и начальные данные подготавливаются отдельно для каждого окружения.

```bash
php bin/reset.php dev
php bin/reset.php test
php bin/phpunit
```

Скрипт принимает только `dev` и `test`, проверяет значение `DATABASE_URL` и удаляет только соответствующий учебный файл _var/agenda.db_ или _var/agenda_test.db_. Затем он применяет миграции и загружает fixtures. При переопределённой внешней базе скрипт прекращает работу. Сброс уничтожает изменения учебных данных выбранного окружения. Функциональные тесты сбрасывают только тестовую БД между сценариями.

В `users` появляются пользователи `alice@example.test`, `bob@example.test` и `admin@example.test` с учебным паролем `study-password`. Первое мероприятие принадлежит Alice, второе Bob. Администратор получает роль `ROLE_ADMIN`. После `authentication` гость читает афишу, а создание требует входа. После `authorization` владелец и администратор могут редактировать и удалять запись, другой пользователь получает 403.

Миграция владельца проходит в два этапа. В `users` столбец nullable и fixtures назначают владельцев. При переходе существующей учебной БД к `authentication` сначала сбрасываются данные в состоянии `users`, затем применяются файлы `authentication` и миграция обязательного владельца. На чистой БД итогового состояния все миграции выполняются до загрузки fixtures. Данные с пустым владельцем останавливают переход к обязательному столбцу.

Сессионный режим CSRF задан в _config/packages/csrf.yaml_ пустым списком `stateless_token_ids`. Токены форм, входа и выхода проверяются с сессией. Тесты отправляют подменённые токены вместе с корректным Origin и подтверждают отказ.

В итоговом состоянии `php bin/console app:events:upcoming 5` выводит ближайшие мероприятия. Вход через форму вызывает `LoginAuditListener`. Русская афиша находится по адресу `/events`, английская по `/en/events`, обе читают одни данные. Правила записи охватывают оба префикса.

Полный список слагов находится в _.examples/stages.json_. Чтобы продолжить работу со своего места, достаточно восстановить соответствующий слаг, установить зависимости и подготовить БД, если состояние её использует. Платформенные упражнения в этот каталог не входят.
